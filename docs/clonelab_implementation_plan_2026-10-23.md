# Darwin CloneLab Repository-Specific Implementation Plan

Date: October 23, 2026

Status: MVP vertical slice implemented on October 23, 2026; advanced assembly and release-reference validation remain staged work.

## Implementation Status

Implemented in the first repository iteration:

- independently callable Python engine plus `/api/v1/clonelab/*` FastAPI routes
- normalized linear/circular sequence identity, FASTA/GenBank import/export, separate project store
- exact Biopython-backed restriction mapping and digestion with circular-origin handling
- sequence-complete intended, reverse, empty-vector, and tandem-insert hypotheses
- single/double-enzyme diagnostic digest optimization with explicit non-identifiability
- render-ready predicted gels, manual band interpretation, and JSON/Markdown reports
- standalone Darwin advanced workspace and eight CloneLab AgentSkills/MCP tools
- local checksum-verified transcript reference registry for Arabidopsis, petunia, and tomato
- compatible-end checks, vector/insert feature remapping, and persisted construct/assay/report artifacts
- synthetic known-truth benchmark (`3/3`) and focused backend tests (`47/47`)

Remaining release-gate work:

- authenticated external plasmid fixtures and independent cross-tool digest comparison
- measured gel calibration data and held-out migration/resolution validation
- complete cut-and-ligate reaction modeling beyond coordinate-defined insertion
- genome FASTA registration for promoter/enhancer interval retrieval; current local references are transcripts
- Darwin gene-view handoff, research-session artifact restoration, and both scientific demonstrations
- expanded direct/HTTP/LLM routing matrices for the new skills and Playwright workflow coverage

## Objective

Add CloneLab to Darwin as a deterministic molecular-design and construct-verification
workflow that begins with an atlas-supported biological target and ends with a traceable
virtual construct, diagnostic assay comparison, predicted gel, and evidence-bounded report.

The defining boundary is:

- Darwin supplies biological candidates, regulatory evidence, genomic context, and reasoning.
- CloneLab supplies authenticated nucleotide sequences and exact molecular calculations.
- The language model orchestrates tools and explains results; it never invents sequence,
  coordinates, cut sites, fragment sizes, construct identity, or gel measurements.

## Current Repository Fit

The repository already provides the main integration surfaces:

- FastAPI application and atlas database service in `backend/main.py`
- deterministic analysis modules such as `backend/sequence_design.py` and `backend/rnai.py`
- a React/Vite workflow shell in `src/GeneNetworkExplorer.jsx`
- shared research context in `src/state/ResearchSessionContext.jsx`
- modular advanced views under `src/components/`
- AgentSkills under `.agents/skills/`
- a structured MCP adapter in `.agents/mcp/grn_atlas_mcp_server.py`
- backend, frontend, end-to-end, direct-skill, and LLM-orchestration test harnesses

CloneLab should use these interfaces without extending their current architectural weaknesses.
In particular, it should not add another large block of models and routes directly to
`backend/main.py`, and it should not store user projects in `backend/data/grn.sqlite3`, which is
regenerated by `make db`.

### Existing capabilities that can be reused

- gene search, candidate ranking, evidence audit, promoter-window coordinates, motif support,
  genome locations, pathways, perturbation predictions, and provenance
- local transcript FASTA loaders in `backend/rnai.py`
- genomic coordinate and sequence-context metadata produced by `fetch_seqctx.py`
- report and collaborator-handoff conventions in `backend/reporting.py` and `backend/packet.py`
- lazy-loaded React views and shared workflow artifacts
- skill and MCP registration/testing infrastructure

### Existing capabilities that are not sufficient

- `backend/sequence_design.py` contains useful sequence utilities, but current primer and CRISPR
  functions are explicitly heuristic and do not provide a molecular object model.
- The atlas stores genomic coordinates and some transcript sequences, but it does not expose an
  authoritative arbitrary-region sequence retrieval service with accession/version provenance.
- There is no GenBank parser/exporter, plasmid topology model, restriction engine, construct
  assembly engine, diagnostic optimizer, gel model, or durable construct-project store.
- Current imported-data tables live in the rebuildable atlas database. That pattern must not be
  used for CloneLab projects.

## Architecture Decisions

### 1. Create a dedicated backend package

Create `backend/clonelab/` with an `APIRouter` mounted by `backend/main.py`.

Planned modules:

| Module | Responsibility |
|---|---|
| `schemas.py` | Pydantic API and domain contracts |
| `sequence.py` | normalization, reverse complement, topology, hashing, coordinate conversion |
| `formats.py` | FASTA/GenBank import and export |
| `reference.py` | local reference-sequence registry and indexed retrieval |
| `restriction.py` | enzyme catalog adapter, recognition sites, cuts, ends, digest products |
| `assembly.py` | sequence-level vector/insert assembly and junction verification |
| `hypotheses.py` | correct, reverse, empty, copy-number, and junction alternatives |
| `diagnostics.py` | digest enumeration, resolvable signatures, and ranking |
| `gel.py` | calibrated migration, resolution, intensity, and lane predictions |
| `interpretation.py` | observed-fragment matching and ambiguity reporting |
| `storage.py` | separate SQLite persistence and schema migration |
| `provenance.py` | sequence, enzyme-data, analysis, and software-version records |
| `safety.py` | scope gate, sequence limits, organism/vector metadata, review flags |
| `reports.py` | JSON, Markdown, FASTA, and GenBank experiment exports |
| `router.py` | `/api/v1/clonelab/*` endpoints only |

The molecular engine must remain callable directly from Python without FastAPI or an LLM.

### 2. Use a separate persistent database

Default path: `backend/data/clonelab.sqlite3`, configurable with `CLONELAB_DB`.

This database is local and gitignored, but unlike the atlas database it is never deleted or
rebuilt by `make db`. Schema changes are handled by explicit versioned migrations in
`clonelab/storage.py`.

Initial tables:

| Table | Purpose |
|---|---|
| `schema_migrations` | CloneLab schema version history |
| `projects` | named research/design workspaces and Darwin context |
| `sequences` | canonical bases, topology, length, SHA-256, accession/version, provenance |
| `features` | typed annotations using normalized coordinates and strand |
| `constructs` | complete assembled sequences and parent/project relationships |
| `construct_components` | ordered vector/insert/backbone components and orientations |
| `reactions` | deterministic transformations and input/output sequence hashes |
| `assays` | digest or verification assay definitions and parameters |
| `hypotheses` | molecular alternatives evaluated by an assay |
| `assay_predictions` | exact fragments, gel signatures, and distinguishability results |
| `observations` | manually entered measured bands and uncertainty |
| `reports` | immutable export metadata and content hashes |
| `audit_events` | imports, calculations, exports, scope-gate decisions |

Large sequence inputs are bounded by configuration. MVP defaults should allow ordinary plasmids
and regulatory inserts while rejecting accidental chromosome-scale uploads. Reference genomes
remain in indexed files, not duplicated into the project database.

### 3. Adopt one coordinate contract

Internal coordinates are zero-based, half-open intervals: `[start, end)`. Strand is `+1` or `-1`.
Circular positions are normalized modulo sequence length. API responses include the internal
coordinates and an explicitly labeled one-based display representation where useful.

Restriction cuts must store top- and bottom-strand cleavage offsets separately. An adapter layer
normalizes library-specific enzyme coordinates before they enter the domain model.

### 4. Add Biopython narrowly

Add a pinned, compatibility-tested Biopython dependency for:

- FASTA and GenBank parsing/export
- sequence and feature primitives
- restriction-enzyme definitions and recognition behavior

Do not make Biopython objects the public API contract. Convert them into CloneLab Pydantic/domain
objects so library upgrades cannot silently change API semantics. Avoid adding a second cloning
framework during the MVP; implement the small required assembly operations explicitly and test
them at the sequence level.

### 5. Keep runtime sequence retrieval local

Darwin currently avoids runtime internet dependencies. Preserve that behavior.

- Extend species configuration with versioned reference FASTA metadata.
- Add `backend/scripts/fetch_clonelab_references.py` to fetch approved references and record URL,
  accession/release, checksum, fetch time, and license notes.
- Build a local index for random-access region retrieval.
- Add `make clonelab-data` as an optional setup target; do not make multi-gigabyte genomes an
  unconditional MVP dependency.
- Begin with Arabidopsis and authenticated reference plasmid fixtures; add petunia only after its
  assembly/gene crosswalk and selected target sequence are verified end to end.

## Domain Invariants

Every phase must preserve these invariants:

1. Sequence identity is represented by normalized bases plus SHA-256.
2. A construct is not valid unless its complete sequence and both junctions are generated.
3. Circular and linear molecules use different digest algorithms.
4. Digest fragment lengths must conserve the parent molecule length.
5. Coincident cut positions are deduplicated without losing enzyme provenance.
6. Zero-cut circular molecules are reported as uncut topology, not falsely modeled as a linear
   fragment with normal migration.
7. Reverse orientation is represented by an actual reverse-complemented insert sequence.
8. Feature coordinates are remapped and revalidated after every assembly transformation.
9. A diagnostic assay may be unique for insert presence but ambiguous for orientation; these are
   separate claims.
10. Restriction patterns cannot establish base-perfect sequence identity unless the differing
    bases alter the tested pattern.
11. Every result includes sequence hashes, topology, enzyme-data version, parameters, software
    version, and warnings.
12. Simulated gels are labeled as predictions and never presented as observations.

## API Plan

All endpoints use `/api/v1/clonelab` and delegate to pure domain functions.

| Endpoint | Phase | Purpose |
|---|---:|---|
| `POST /projects` | 1 | Create a durable project from Darwin or standalone context |
| `GET /projects/{project_id}` | 1 | Retrieve project metadata and artifact links |
| `POST /sequences/import` | 1 | Parse FASTA or GenBank text with topology/provenance |
| `POST /sequences/retrieve` | 1/6 | Retrieve a local reference interval by assembly/accession |
| `GET /sequences/{sequence_id}` | 1 | Return metadata, features, and optionally bases |
| `POST /restriction/map` | 2 | Return normalized sites and cut coordinates |
| `POST /digests` | 2 | Return exact digest products and fragment sequences |
| `POST /constructs` | 3 | Assemble a complete virtual construct and verify junctions |
| `GET /constructs/{construct_id}` | 3 | Return construct sequence, map data, and provenance |
| `POST /constructs/{id}/hypotheses` | 3 | Generate requested alternative construct states |
| `POST /gels/simulate` | 4 | Return lane/band data with model version and uncertainty |
| `POST /assays/optimize` | 4 | Rank digests against explicit construct hypotheses |
| `POST /results/interpret` | 5 | Compare manually entered bands with predictions |
| `POST /reports/export` | 5 | Export reproducible JSON/Markdown/FASTA/GenBank artifacts |

Every mutation endpoint supports a dry-run mode. Deterministic calculation endpoints accept
inline sequences for stateless use and stored IDs for project workflows.

### Phase 3 - Sequence-level assembly and construct hypotheses

Purpose: create verified recombinant molecules, not diagrams that merely imply assembly.

Files:

- `backend/tests/clonelab/test_assembly.py`
- `backend/tests/clonelab/test_hypotheses.py`

Initial supported assembly mode:

- restriction/ligation at explicit compatible ends
- insertion into a circular vector at one defined cloning interval

Tasks:

1. Verify end compatibility rather than accepting labels alone.
2. Generate the complete construct sequence and both junction sequences.
3. Re-run restriction mapping on the assembled sequence.
4. Remap vector and insert features into construct coordinates.
5. Generate explicit hypotheses: intended, reverse, empty vector, tandem insert, and user-supplied

6. Reject impossible assemblies with machine-readable reasons.

Deferred assembly modes:

- synthesis/vendor optimization and procurement

Acceptance gate:

- complete construct sequences and junctions match independently assembled references exactly
- reverse orientation uses the exact reverse complement and correct feature strands
- re-digestion of every construct hypothesis is reproducible from its stored sequence hash
- no construct is marked verified from length arithmetic alone

### Phase 4 - Gel model and diagnostic assay optimization

Purpose: identify assays that discriminate molecular states and show their predicted observations.

Files:

- `backend/clonelab/gel.py`
- `backend/clonelab/diagnostics.py`
- `backend/clonelab/calibration/*.json`
- `backend/scripts/benchmark_clonelab_gels.py`
- `backend/scripts/benchmark_clonelab_diagnostics.py`
- `backend/tests/clonelab/test_gel.py`
- `backend/tests/clonelab/test_diagnostics.py`

Gel model tasks:

1. Represent named ladders as versioned data with source notes.
2. Support an idealized calibrated profile and user-supplied calibration points.
3. Return normalized migration, uncertainty intervals, relative intensity, and merged-band groups.
4. Model visibility limits and resolution without claiming exact physical migration for every gel.
5. Treat uncut circular topology separately from linear fragment lanes.
6. Return render-ready data; the frontend draws the gel.

Diagnostic optimizer tasks:

1. Enumerate allowed single- and double-enzyme candidates from a configurable enzyme set.
2. Convert each hypothesis into a resolvable band signature under the selected gel model.
3. Score:
   - fraction of hypotheses uniquely identified
   - pairwise hypothesis separation
   - orientation-specific discrimination
   - insert-presence discrimination
   - minimum resolvable separation
   - invisible/merged fragments
   - assay complexity and configured reagent constraints
4. Use deterministic signature entropy/information gain for the MVP.
5. Return `no_unique_digest` when the candidate set cannot answer the requested question.
6. Recommend a supplementary assay category without claiming it has already been designed.

Acceptance gate:

- migration is monotonic with fragment size within each calibrated range
- held-out ladder migration has median absolute error no greater than 5% of lane length
- held-out resolvable/unresolvable band-pair classification is at least 90% accurate
- synthetic diagnostic cases recover the known best digest or an explicitly equivalent tie
- impossible discrimination cases are reported as ambiguous, never forced into a winner

## MVP Success Criteria

The MVP is complete when a user can:

1. Import validated FASTA and GenBank records.
2. Work with circular and linear sequence objects without coordinate ambiguity.
3. Create a sequence-complete virtual recombinant plasmid.
4. Inspect construct topology, orientation, features, and junctions.
5. Calculate exact single- and double-enzyme digest products against reference cases.
6. Compare intended, reverse, and empty-vector hypotheses.
7. Rank candidate diagnostic digests and distinguish insert detection from orientation confirmation.
8. Render a calibrated, explicitly simulated gel with fragment traceability.
9. Enter measured band sizes and receive all compatible interpretations.
10. Export a reproducible report with sequence hashes and versioned provenance.
11. Launch the workflow from a Darwin-supported biological target.

## Validation Matrix

| Layer | Required validation |
|---|---|
| Sequence parsing | exact bases, topology, features, invalid alphabet, malformed files |
| Coordinates | strand conversion, origin crossing, rotation, insert remapping |
| Restriction | zero/one/many cuts, circular/linear, coincident/overlapping sites, double digest |
| Assembly | compatibility, forward/reverse insert, empty/tandem alternatives, exact junctions |
| Molecular identity | independent full-sequence hash and junction comparison |
| Gel | ladder calibration, monotonicity, band merge, intensity, visibility, topology warnings |
| Optimization | unique, tied, and impossible discrimination cases |
| Interpretation | missing, extra, merged, and uncertain bands; multiple compatible hypotheses |
| Persistence | migrations, restart recovery, concurrent reads, atlas rebuild isolation |
| API | schema, limits, errors, stateless/stored equivalence, provenance |
| UI | accessible tables, map/band linkage, project recovery, export |
| Skills/MCP | direct/HTTP parity, correct routing, structured units, no LLM arithmetic |
| Integration | clean-clone setup, Darwin handoff, no existing test regressions |

## Deferred Scope

The following should not delay the MVP:

- automated primer design and PCR thermodynamic optimization
- genome-wide primer specificity
- Gibson, Golden Gate, Gateway, and arbitrary homology assembly
- Southern blot design
- automated gel-image band detection
- partial-digest kinetic modeling
- supercoiled/nicked migration prediction beyond explicit warnings or empirical calibration
- instrument integration
- procurement, synthesis ordering, or automated laboratory execution
- unrestricted organism/vector support
- advanced probabilistic interpretation and learned image models

Existing heuristic primer/CRISPR functions remain available but must not be presented as CloneLab
sequence verification until separately upgraded and validated.

## Post-MVP Completion Workstreams

These workstreams complete proposal capabilities that are intentionally outside the first release.

### R2 - PCR construct verification

- accept explicit primer sequences and perform exact in-silico PCR against every construct
  hypothesis
- report zero, one, or multiple amplicons with strand, coordinates, and product sequence
- compare junction-spanning, insert-internal, and vector-flanking assay designs
- add a validated thermodynamic/specificity engine before offering automated primer selection
- keep current `sequence_design.primer_design` labeled as heuristic until it passes the new
  external comparator suite

### R3 - Assisted gel-image interpretation

- accept an uploaded gel image only after upload limits and image sanitization are implemented
- require ladder/lane calibration or explicit user annotation
- preserve the original image hash and every manual/automatic correction
- treat band detection as a proposed measurement with confidence, never as molecular identity
- compare extracted measurements through the same deterministic interpretation engine used for
  manually entered bands

### R4 - Probabilistic assay interpretation

- add hypothesis priors, migration-error distributions, dropout, merged bands, and partial-digest
  alternatives
- rank observations by likelihood and posterior support while retaining raw deterministic matches
- validate calibration on held-out measured gels before presenting probabilities to users

### R5 - Additional assembly methods

- add Golden Gate only after type-IIS cut semantics and scar/junction validation are complete
- add Gibson/homology assembly with explicit overlap and complete-product sequence checks
- add other recombination systems individually rather than through a generic unvalidated operation

### R6 - Education and assessment mode

- create versioned hidden-state exercises from validated construct hypotheses
- provide feedback based on assay identifiability and evidence limits
- keep exercise data separate from research project records

## Engineering Forecast

The proposal's 10–12 week estimate is plausible for a reduced prototype, but not for the full MVP
above with independent reference validation, persistent projects, accessible UI, Darwin handoff,
skills/MCP exposure, and two reproducible demonstrations. A more defensible single-developer
forecast is:

| Delivery slice | Expected effort |
|---|---:|
| Phase 0 contracts and fixtures | 1–2 weeks |
| Phase 1 sequence/store foundation | 2 weeks |
| Phase 2 restriction engine | 2 weeks |
| Phase 3 assembly and hypotheses | 2–3 weeks |
| Phase 4 gel and optimizer | 2–3 weeks |
| Phase 5 UI, interpretation, reports | 3 weeks |
| Phase 6 Darwin integration | 2 weeks |
| Phase 7 skills and MCP | 1–2 weeks |
| Phase 8 demonstrations and release validation | 2 weeks |

Expected full MVP: approximately 17–21 developer weeks if completed serially. This can be shortened
by limiting the first release to imported sequences, restriction/ligation, manual observations,

## Risks and Mitigations

| Risk | Repository-specific mitigation |
|---|---|
| User designs disappear during `make db` | separate `clonelab.sqlite3`; explicit migration tests |
| `main.py` grows further | mount a dedicated router; keep domain logic in `backend/clonelab/` |
| Existing heuristic tools are mistaken for validated molecular engines | separate package/API names and explicit capability labels |
| Reference coordinates exist but bases are unavailable | versioned local reference registry and readiness errors |
| Circular-origin errors | one coordinate contract plus exhaustive origin-crossing tests |
| Library upgrade changes enzyme behavior | adapter, pinned version, catalog version in every result, held-out regressions |
| Gel graphic implies experimental certainty | calibrated model IDs, uncertainty, simulation watermark, topology warnings |
| Optimizer overclaims identity | separate presence/orientation/base-identity claims and return non-identifiability |
| Petunia identifiers or paralogs are misassigned | assembly/cultivar/family reconciliation gate before demonstration |
| Uploaded sequence creates resource pressure | request limits, bounded parsing, normalized storage, explicit failures |
| Biological misuse or out-of-scope construct | approved-scope metadata, deterministic review flags, audit trail, no procurement/execution |
| Skills encourage LLM arithmetic | structured deterministic tools and adversarial orchestration tests |

## Recommended Working Order

Implementation priority was refined on October 23, 2026: diagnostic digest optimization is the
first differentiating vertical slice. It still depends on exact sequence, restriction, and
construct-hypothesis primitives, but those prerequisites should be implemented narrowly before
broader project management, gel graphics, or educational UI work.

Implement and merge one gated slice at a time:

1. Phase 0 contracts and diagnostic fixtures
2. minimal Phase 1 sequence primitives, callable directly from Python
3. Phase 2 restriction engine
4. minimal Phase 3 explicit construct hypotheses
5. Phase 4 diagnostic digest optimizer and its FastAPI endpoint
6. remaining Phase 1 persistence/import/export foundation
7. remaining Phase 3 assembly workflows and Phase 4 gel rendering
8. Phase 5 standalone UI, interpretation, and reports
9. Phase 6 Darwin sequence handoff
10. Phase 7 skills and MCP exposure
11. Phase 8 demonstrations and release validation

Do not begin the interactive plasmid map, AI skills, or public demonstrations before the
sequence, restriction, and assembly gates pass. This ordering prevents attractive visual output
from outrunning molecular correctness.

## First Implementation Milestone

The first implementation iteration should complete Phase 0 and the smallest vertical slice of
Phase 1:

1. add the CloneLab package and schemas
2. establish the separate database and migration mechanism
3. import and retrieve one circular GenBank plasmid and one linear FASTA insert
4. preserve sequence hashes, topology, features, and provenance
5. expose the sequence import/get API
6. add backend tests and clean-repository setup documentation

That milestone is independently useful, low-risk to existing Darwin behavior, and establishes the
contracts required by every later phase.
